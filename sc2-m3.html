Before you begin

When an attack happens, logs and alerts decide whether you notice it in minutes or months. Error handling decides whether a failure locks the door or leaves it open. This module covers both.

Have Juice Shop ready.

1

Theory: logging, alerting and exceptional conditions

What to log and never log, protecting logs, alerting, and handling errors safely.

Why logging and alerting matter

Many breaches go unnoticed for months. Without useful logs and alerts, nobody sees an attack while it happens, and afterwards nobody can tell what was taken. Logging is also how you meet audit duties and investigate disputes.

What to log

  • Sign-in successes and failures, sign-outs, password and MFA changes.
  • Access-control failures (Course 1, Module 2) and input that fails validation.
  • Admin actions, permission changes and changes to important data, such as order status or bank details.
  • Errors and unexpected conditions, with a request ID that links them to the user's request.

Each entry should record when it happened, who did it, from where, what they tried to do, and the result.

What never to log

  • Passwords, even wrong ones, which are often a real password with a typo.
  • Session IDs, access tokens, API keys and encryption keys.
  • Full card numbers, bank details, and personal data the log does not need.

Protecting the logs

  • Use structured logs (for example JSON) from a logging library, not text joined by hand. This also stops log injection, where a user puts a line break in their input to add a fake log entry.
  • Send logs to a central system that applications can write to but not change or delete, and limit who can read them.
  • Never make log files reachable from the web.
  • Keep logs for an agreed period, long enough for investigations and audits.

Alerting

Logs help only if someone looks at the important events. Set alerts for patterns such as many failed sign-ins for one account, many access-control failures from one user, or admin actions at unusual times. Agree who receives each alert and what they do next.

Handling exceptional conditions

  • Fail closed. When a security check cannot complete (a timeout, an error from another service), refuse the action.
  • Catch errors where you can handle them, and have one handler for everything else that logs the details and shows a general message (Course 1, Module 3).
  • Release resources such as files, connections and locks in finally or using blocks, so errors do not leave them open.
  • Set timeouts and limits on calls to other services, and on the size of uploads and requests.
  • Check return values. A function that reports failure through its return value is easy to ignore.

OWASP mapping

Where these weaknesses sit in the OWASP Top 10:2025, with their CWE numbers.

This module maps to two categories. A09:2025 Logging and Alerting Failures covers missing or unsafe logs and alerts. A10:2025 Mishandling of Exceptional Conditions is new in 2025, and covers errors and unusual situations that leave the system in an unsafe state.

WeaknessCWEOWASP Top 10:2025
Security events are not loggedCWE-778: Insufficient LoggingA09 Logging and Alerting Failures
User input can add fake lines to a logCWE-117: Improper Output Neutralization for LogsA09 Logging and Alerting Failures
Secrets or personal data are written to logsCWE-532: Insertion of Sensitive Information into Log FileA09 Logging and Alerting Failures
Errors are not handled, or handled wronglyCWE-755: Improper Handling of Exceptional ConditionsA10 Mishandling of Exceptional Conditions
An error causes the action to be allowedCWE-636: Not Failing Securely ('Failing Open')A10 Mishandling of Exceptional Conditions
Watch out

An empty catch block, or one that only logs and carries on, is a common way to fail open. Ask "what state is the system in now?" every time you catch an error.

Fixes: structured logs and failing closed

Logging and error handling with the weakness and fixed, in each language.

The examples show two fixes in each language: logging a security event as structured data without secrets, and making a security check fail closed when the service it depends on fails.

Node.js

pino writes JSON log lines and can remove sensitive fields.

With the weakness

console.log("login failed for " + email + " with password " + password);

try {
  ok = await riskService.check(payment);
} catch (err) {
  ok = true;                         // fails open
}

Fixed

import pino from "pino";
const log = pino({ redact: ["password", "token", "req.headers.authorization"] });

log.warn({ event: "login_failed", email, ip: req.ip, requestId: req.id });

let ok;
try {
  ok = await riskService.check(payment, { timeout: 3000 });
} catch (err) {
  log.error({ event: "risk_check_failed", requestId: req.id, err });
  ok = false;                        // fails closed
}
JavaScript (browser)

Browser code can report errors to the server, but must not send tokens or personal data with them.

With the weakness

window.onerror = (msg) => {
  fetch("/api/client-errors", {
    method: "POST",
    body: JSON.stringify({ msg, token: localStorage.getItem("token"), page: location.href }),
  });
};

Fixed

window.onerror = (msg) => {
  fetch("/api/client-errors", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ msg: String(msg).slice(0, 500), page: location.pathname }),
  });                                // no tokens, no query strings
};
TypeScript

A typed result makes the failure case impossible to ignore.

With the weakness

async function canRefund(orderId: string): Promise<boolean> {
  try {
    return await fraudApi.check(orderId);
  } catch {
    return true;                     // the fraud service is down, so allow it
  }
}

Fixed

type Decision = { allowed: true } | { allowed: false; reason: string };

async function canRefund(orderId: string): Promise<Decision> {
  try {
    const ok = await fraudApi.check(orderId, { signal: AbortSignal.timeout(3000) });
    return ok ? { allowed: true } : { allowed: false, reason: "flagged" };
  } catch (err) {
    logger.error({ event: "fraud_check_failed", orderId, err });
    return { allowed: false, reason: "check unavailable" };   // fails closed
  }
}

C#

ILogger message templates keep values as separate fields.

With the weakness

_logger.LogInformation("Login failed for " + email + " password " + password);

bool ok;
try { ok = await _risk.CheckAsync(payment); }
catch { ok = true; }                  // fails open

Fixed

_logger.LogWarning("login_failed {Email} {Ip} {RequestId}", email, ip, requestId);

bool ok = false;
try
{
    using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(3));
    ok = await _risk.CheckAsync(payment, cts.Token);
}
catch (Exception ex)
{
    _logger.LogError(ex, "risk_check_failed {RequestId}", requestId);
    ok = false;                       // fails closed
}
Recommended practice
  • Add a request ID to every log entry and every error message, so one user's problem can be traced across services.
  • Test the failure paths: stop the dependency, or make it time out, and check the result is a refusal.
  • Review alerts after each incident and false alarm, and adjust them.

Java

Java has no built-in JSON writer, so the starter includes quote(), which turns a value into a safe JSON string. Use it.

Logging.java

import java.util.function.IntPredicate;

public class Logging {
    // Turns a value into a JSON string, escaping quotes and line breaks.
    static String quote(String s) {
        StringBuilder b = new StringBuilder("\"");
        for (char c : s.toCharArray()) {
            switch (c) {
                case '"' -> b.append("\\\"");
                case '\\' -> b.append("\\\\");
                case '\n' -> b.append("\\n");
                case '\r' -> b.append("\\r");
                default -> { if (c < 0x20) b.append(String.format("\\u%04x", (int) c)); else b.append(c); }
            }
        }
        return b.append('"').toString();
    }

    // TODO: return one JSON line, with password=, token= and secret= values replaced by [REDACTED]
    static String logEvent(String event, String user, String detail) {
        return event + " user=" + user + " " + detail;
    }

    // TODO: fail closed when riskCheck throws
    static String authorizePayment(int amount, IntPredicate riskCheck) {
        try {
            return riskCheck.test(amount) ? "approved" : "declined";
        } catch (RuntimeException e) {
            return "approved";
        }
    }

    public static void main(String[] args) {
        IntPredicate lowRisk = a -> true;
        IntPredicate highRisk = a -> false;
        IntPredicate serviceDown = a -> { throw new IllegalStateException("risk service timed out"); };
        System.out.println("1 " + logEvent("login_failed", "alice", "wrong password"));
        System.out.println("2 " + logEvent("login_failed", "alice\n2026-11-07 INFO login_ok user=admin", ""));
        System.out.println("3 " + logEvent("api_call", "bob", "GET /orders?token=abc123&page=2"));
        System.out.println("4 " + authorizePayment(50, lowRisk));
        System.out.println("5 " + authorizePayment(5000, highRisk));
        System.out.println("6 " + authorizePayment(100, serviceDown));
    }
}
