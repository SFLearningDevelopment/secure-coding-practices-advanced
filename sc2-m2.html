Before you begin

Most of the code in your app was written by someone else, and your build pipeline can change what you ship. This module covers dependency scanning, SBOMs, safe CI/CD pipelines, Subresource Integrity and safe deserialisation.

Have Juice Shop ready, and the dependency and SBOM tools from Module 0.

1

Theory: dependencies, pipelines and integrity

How the supply chain is attacked, and the practices that protect it.

Your app is mostly other people's code

A typical web app pulls in hundreds of open-source packages, most of them indirectly (dependencies of your dependencies). Your build tools, base container images and CI/CD pipeline are part of the supply chain too. A weakness anywhere in this chain becomes a weakness in your app.

Ways the supply chain is attacked

  • Known weaknesses in old versions of packages, published as CVEs.
  • Malicious packages, including names that look like popular ones (typosquatting) and public packages named like your private ones (dependency confusion).
  • Hijacked maintainers or packages, where a trusted package suddenly ships harmful code in a new version.
  • Compromised build pipelines, for example a third-party GitHub Action that is changed to steal secrets.
  • Scripts loaded from other servers, such as a content delivery network (CDN), that are changed after you added them.

Recommended practices for dependencies

  • Commit the lock file (package-lock.json, poetry.lock, packages.lock.json) and install from it in CI (npm ci, not npm install).
  • Scan dependencies on every build with software composition analysis (SCA) tools, and fail the build on high-severity findings.
  • Keep an SBOM (software bill of materials) for each release, in a standard format such as CycloneDX or SPDX, so you can answer "are we affected?" within minutes when a new CVE appears.
  • Update regularly, with automated pull requests (Dependabot or Renovate), and remove packages you no longer use.
  • Prefer well-maintained packages, and use a private registry or scoped package names for internal packages.

Integrity: making sure code and data are what you expect

  • Pin third-party GitHub Actions to a full commit SHA, not a tag that can be moved, and give the workflow's GITHUB_TOKEN only the permissions it needs.
  • Protect the main branch: require reviews and passing checks before merging.
  • Sign build outputs (for example container images with Sigstore cosign) and check the signature before deploying.
  • Use Subresource Integrity (SRI) for any script or stylesheet loaded from another server, so the browser refuses it if it changes.
  • Never deserialise untrusted data with formats that can create any object, such as Python pickle, Java ObjectInputStream or .NET BinaryFormatter. Use JSON into a fixed data type, and validate it.

OWASP mapping

Where these weaknesses sit in the OWASP Top 10:2025, with their CWE numbers.

This module maps to two categories. A03:2025 Software Supply Chain Failures is new in 2025 and widens the 2021 category "Vulnerable and Outdated Components" to the whole supply chain. A08:2025 Software or Data Integrity Failures covers code and data that are trusted without checking.

Watch out

A clean scan today does not mean a clean app tomorrow. New CVEs are published every day for packages you already use, so scans and SBOM checks must run regularly, not only when the code changes.

Fixes: lock files, scanning, signing and safe parsing

The main fixes with the weakness and fixed, in each language and in GitHub Actions.

The examples cover the main fixes: installing from lock files and scanning in CI, checking scripts loaded from CDNs, never running or deserialising untrusted data as code, and locking down CI pipelines.

Node.js

Install exactly what the lock file says, and fail the build on high-severity findings.

With the weakness

# CI script
npm install                     # may pull newer, unchecked versions
npm run build

Fixed

# CI script
npm ci                          # installs exactly what package-lock.json says
npm audit --audit-level=high    # fails the build on high or critical findings
npx @cyclonedx/cyclonedx-npm --output-file sbom.json
npm run build
JavaScript (browser)

A script loaded from a CDN can be changed by whoever controls the CDN. Subresource Integrity lets the browser check it.

With the weakness

<script src="https://cdn.example.com/chart-4.4.1.min.js"></script>

Fixed

<script src="https://cdn.example.com/chart-4.4.1.min.js"
        integrity="sha384-HASH_OF_THE_EXACT_FILE"
        crossorigin="anonymous"></script>
<!-- The browser refuses to run the file if its hash does not match. -->
TypeScript

Data from outside is parsed as JSON and validated, never run as code.

With the weakness

// settings arrive as text from a partner's API
const settings = eval("(" + body + ")");          // runs any code inside

Fixed

import { z } from "zod";

const Settings = z.object({ theme: z.enum(["light", "dark"]), pageSize: z.number().int().max(100) }).strict();
const settings = Settings.parse(JSON.parse(body)); // data only, checked shape
Python

Pin packages with hashes, and never unpickle data from outside.

With the weakness

# requirements.txt
requests

# app.py
profile = pickle.loads(request.data)               # can run any code

Fixed

# requirements.txt (made with pip-compile --generate-hashes)
requests==2.32.3 \
    --hash=sha256:...

# CI:  pip install --require-hashes -r requirements.txt

# app.py
profile = Profile.model_validate_json(request.data)   # pydantic, data only
Java

Read JSON into a fixed record type. Never use ObjectInputStream on data from outside.

With the weakness

ObjectInputStream in = new ObjectInputStream(request.getInputStream());
Profile p = (Profile) in.readObject();   // any class on the classpath can be created

Fixed

public record Profile(String name, int pageSize) {}

ObjectMapper mapper = JsonMapper.builder()
    .enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
    .build();
Profile p = mapper.readValue(request.getInputStream(), Profile.class);
// Do not turn on Jackson's default typing for data from outside.
C#

BinaryFormatter is unsafe and removed in .NET 9. Use System.Text.Json into a fixed type.

With the weakness

var formatter = new BinaryFormatter();
var profile = (Profile)formatter.Deserialize(Request.Body);

Fixed

public record Profile(string Name, int PageSize);

var options = new JsonSerializerOptions
{
    UnmappedMemberHandling = JsonUnmappedMemberHandling.Disallow
};
var profile = await JsonSerializer.DeserializeAsync<Profile>(Request.Body, options);
GitHub Actions

Pin third-party actions to a full commit SHA, and limit the token's permissions.

With the weakness

on: push
jobs:
  build:
    runs-on: ubuntu-latest          # token gets the default permissions
    steps:
      - uses: some-org/setup-tool@v2   # a tag can be moved to new code

Fixed

on: push
permissions:
  contents: read                    # only what the job needs
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683   # v4.2.2
      - uses: some-org/setup-tool@0123456789abcdef0123456789abcdef01234567   # v2.1.0
Recommended practice
  • Store the SBOM with each release, and check it when a major CVE is announced.
  • Review new dependencies before adding them: who maintains it, how often it is updated, and how many other packages it brings in.
  • Turn on Dependabot alerts and security updates for every repository.

Lab: find a weak library, then scan and upgrade

Part A: Forgotten Developer Backup and Vulnerable Library in Juice Shop. Part B: scan, upgrade and create an SBOM.

Part A: find a weak dependency in Juice Shop

Start Juice Shop on 127.0.0.1.

  1. In Course 1 you found the /ftp folder. It holds package.json.bak, a backup of Juice Shop's dependency list, but the server only serves .md and .pdf files from that folder.
  2. Open http://localhost:3000/ftp/package.json.bak%2500.md. The encoded "null byte" (%2500) tricks the file-type check, and the backup downloads. Juice Shop shows a banner for Forgotten Developer Backup.
  3. Open the downloaded file and look at the dependencies list. Look up a few of the packages and versions in the OSV database or the GitHub Advisory Database. One of them, sanitize-html 1.4.2, has known weaknesses that let attackers get scripts past it.
  4. Go to Customer Feedback, and send a comment naming the library and its version, for example sanitize-html 1.4.2 has known security weaknesses, with any rating.

Juice Shop shows a banner for the Vulnerable Library challenge.

Think about it

The SBOM you create in Part B is exactly the list an attacker had to steal here. With an SBOM and a scanner in CI, the team would have known about this weakness before an attacker did.

Part B: scan, upgrade and record your dependencies

In each block you install an old package with known weaknesses, scan it, upgrade it, scan again, and create an SBOM. The browser block practises Subresource Integrity instead.

Node.js
mkdir sc2-m2-node && cd sc2-m2-node
npm init -y
npm install lodash@4.17.15            # an old version with known weaknesses
npm audit                             # 1. note the findings
npm install lodash@latest             # 2. upgrade
npm audit                             # 3. "found 0 vulnerabilities"
npx @cyclonedx/cyclonedx-npm --output-file sbom.json   # 4. create the SBOM
JavaScript (browser)

Work out the SRI hash of a script and use it in a page.

mkdir sc2-m2-sri && cd sc2-m2-sri
echo 'document.body.append("Script loaded");' > hello.js
openssl dgst -sha384 -binary hello.js | openssl base64 -A    # copy the output

index.html

<!doctype html>
<body>
<script src="hello.js" integrity="sha384-PASTE_THE_HASH_HERE" crossorigin="anonymous"></script>
</body>
python3 -m http.server 8000 --bind 127.0.0.1   # open http://127.0.0.1:8000

The page shows "Script loaded". Now change one letter in hello.js and reload: the browser refuses to run it, and the console shows an integrity error.

TypeScript

The same steps as Node.js. TypeScript projects use npm, so npm audit and the CycloneDX npm tool apply.

mkdir sc2-m2-ts && cd sc2-m2-ts
npm init -y
npm install lodash@4.17.15 && npm install --save-dev typescript
npm audit
npm install lodash@latest
npm audit
npx @cyclonedx/cyclonedx-npm --output-file sbom.json
Python

pip-audit checks a requirements file without installing it, so the scanner's own packages do not get mixed up with your app's.

mkdir sc2-m2-py && cd sc2-m2-py
python3 -m venv .venv
source .venv/bin/activate              # Windows: .venv\Scripts\activate
pip install pip-audit cyclonedx-bom
echo "requests==2.19.0" > requirements.txt          # an old version with known weaknesses
pip-audit -r requirements.txt          # 1. note the findings and the "Fix Versions" column
# 2. change requirements.txt to the latest version of requests (see pypi.org/project/requests)
pip-audit -r requirements.txt          # 3. no findings for requests
cyclonedx-py requirements requirements.txt -o sbom.json   # 4. create the SBOM
Java

Create a Maven project with an old version of Apache Commons Text, which has a known critical weakness (CVE-2022-42889).

pom.xml

<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>sf.lab</groupId>
  <artifactId>supply-chain-demo</artifactId>
  <version>1.0</version>
  <dependencies>
    <dependency>
      <groupId>org.apache.commons</groupId>
      <artifactId>commons-text</artifactId>
      <version>1.9</version>
    </dependency>
  </dependencies>
</project>
mvn org.owasp:dependency-check-maven:check -DnvdApiKey=YOUR_KEY   # 1. open target/dependency-check-report.html
# 2. change the version to 1.12.0 in pom.xml, then run the check again
mvn org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom             # 3. SBOM in target/
C#
dotnet new console -o sc2-m2-cs
cd sc2-m2-cs
dotnet add package Newtonsoft.Json --version 12.0.1   # an old version with a known weakness
dotnet list package --vulnerable --include-transitive # 1. note the finding
dotnet add package Newtonsoft.Json                    # 2. upgrade to the latest version
dotnet list package --vulnerable --include-transitive # 3. no findings
dotnet CycloneDX sc2-m2-cs.csproj -o .                # 4. create the SBOM
