1

Theory: threat modelling and business logic

The four questions, data-flow diagrams, STRIDE, business-logic flaws and secure design patterns.

Threat modelling

Threat modelling means looking at a design before it is built, and asking what could go wrong. It finds design gaps that no amount of careful coding will fix later. It works best as a short, regular team activity, for example when a new feature is designed. A common way to run it is to answer four questions:

  1. What are we working on? Draw a simple data-flow diagram.
  2. What can go wrong? Go through each part of the diagram with STRIDE.
  3. What are we going to do about it? Choose a control for each important threat.
  4. Did we do a good job? Check that the controls were built and tested.

Data-flow diagrams

A data-flow diagram shows external entities (users, other companies' systems), processes (your services), data stores (databases, files, queues), the data flows between them, and the trust boundaries that data crosses (Course 1, Module 1).

DDenial of service: making the system unavailableThousands of expensive searches a secondRate limits, timeouts, size limits

Business-logic flaws

Business-logic flaws are weaknesses in the rules of the application, not in its technology. Scanners rarely find them, because each request looks normal. Common examples:

  • Skipping steps. Calling "ship order" before "pay for order".
  • Breaking limits. Using a single-use coupon many times, or ordering a negative quantity.
  • Race conditions. Sending two withdrawal requests at the same instant so both pass the balance check.
  • Trusting values the client should not choose, such as a rating, a status or a price.

Secure design patterns

  • Keep the workflow on the server. Store each order's state and allow only the transitions the business permits.
  • Write abuse cases next to user stories: "As an attacker, I want to ship an unpaid order".
  • Make important operations idempotent, for example with an idempotency key, so repeating a request does not repeat the effect.
  • Limit how often a user can perform sensitive actions, such as applying coupons or sending messages.

Signs of insecure design in a review

  • A status, price, discount or rating is accepted from the request.
  • A multi-step process (checkout, sign-up, password reset) has no record on the server of which steps are done.
  • A check and the action it protects happen in separate requests, with nothing to stop the state changing in between.
  • Nobody can say what should happen if a step is called twice, out of order, or by the wrong user.
Watch out

A design flaw cannot be fixed by a library or a scanner rule. It is fixed by changing what the system does, which is much cheaper before the code is written.

3

Fixes: keep the workflow on the server

An order workflow with the weakness and fixed, in each language.

The example is an order workflow: created, paid, shipped, delivered, or cancelled. With the weakness, the client sends any new status and the server saves it, so an unpaid order can be shipped. The fix in every language: keep the status on the server, allow only the permitted transitions, and give each step its own endpoint with its own permission check.

Node.js

Express. The order's current status is stored on the server, and the change is checked against the allowed transitions.

With the weakness

app.post("/api/orders/:id/status", requireLogin, async (req, res) => {
  // the client chooses the new status, and nothing checks the current one
  await orders.update(req.params.id, { status: req.body.status });
  res.sendStatus(204);
});

Fixed

const ALLOWED = {
  created: ["paid", "cancelled"],
  paid: ["shipped", "cancelled"],
  shipped: ["delivered"],
};

app.post("/api/orders/:id/ship", requireRole("warehouse"), async (req, res) => {
  const order = await orders.findById(req.params.id);
  if (!order) return res.sendStatus(404);
  if (!(ALLOWED[order.status] || []).includes("shipped")) {
    return res.status(409).json({ error: "Order cannot be shipped in its current state" });
  }
  await orders.update(order.id, { status: "shipped" });
  res.sendStatus(204);
});
JavaScript (browser)

Disabled buttons and hidden steps in the page are not controls. Anyone can turn a button back on in the developer tools.

With the weakness

// The Ship button is only enabled after payment, so the developer
// assumes unpaid orders can never be shipped
shipButton.disabled = order.status !== "paid";

Fixed

// The button state is only a hint for the user. The server refuses
// the request (409) if the order is not paid, whatever the page shows.
shipButton.disabled = order.status !== "paid";
const res = await fetch(`/api/orders/${order.id}/ship`, { method: "POST" });
if (res.status === 409) showMessage("This order cannot be shipped yet.");
TypeScript

A typed state machine makes the allowed transitions easy to review and test.

With the weakness

type Status = "created" | "paid" | "shipped" | "delivered" | "cancelled";

async function setStatus(id: string, next: Status) {
  await orders.update(id, { status: next });      // any status, any time
}

Fixed

type Status = "created" | "paid" | "shipped" | "delivered" | "cancelled";

const ALLOWED: Record<Status, Status[]> = {
  created: ["paid", "cancelled"],
  paid: ["shipped", "cancelled"],
  shipped: ["delivered"],
  delivered: [],
  cancelled: [],
};

async function setStatus(id: string, next: Status): Promise<void> {
  const order = await orders.findById(id);
  if (!ALLOWED[order.status as Status].includes(next)) {
    throw new ConflictError(`Cannot move order from ${order.status} to ${next}`);
  }
  await orders.update(id, { status: next });
}
Python

The transition check also runs inside one database transaction, so two requests cannot both pass it.

With the weakness

@app.post("/api/orders/{order_id}/status")
def set_status(order_id: int, body: StatusChange, user=Depends(current_user)):
    db.execute(update(Order).where(Order.id == order_id).values(status=body.status))

Fixed

ALLOWED = {
    "created": {"paid", "cancelled"},
    "paid": {"shipped", "cancelled"},
    "shipped": {"delivered"},
}

@app.post("/api/orders/{order_id}/ship")
def ship(order_id: int, user=Depends(require_role("warehouse"))):
    with db.begin():
        order = db.get(Order, order_id, with_for_update=True)   # lock the row
        if order is None:
            raise HTTPException(404)
        if "shipped" not in ALLOWED.get(order.status, set()):
            raise HTTPException(409, "Order cannot be shipped in its current state")
        order.status = "shipped"
Java

Spring Boot. An enum holds the allowed transitions.

With the weakness

@PostMapping("/api/orders/{id}/status")
public void setStatus(@PathVariable long id, @RequestBody StatusChange change) {
    Order o = orders.findById(id).orElseThrow(NotFound::new);
    o.setStatus(change.status());              // any status, any time
    orders.save(o);
}

Fixed

public enum Status {
    CREATED, PAID, SHIPPED, DELIVERED, CANCELLED;

    boolean canMoveTo(Status next) {
        return switch (this) {
            case CREATED -> next == PAID || next == CANCELLED;
            case PAID -> next == SHIPPED || next == CANCELLED;
            case SHIPPED -> next == DELIVERED;
            default -> false;
        };
    }
}

@Transactional
@PostMapping("/api/orders/{id}/ship")
public void ship(@PathVariable long id) {
    Order o = orders.findByIdForUpdate(id).orElseThrow(NotFound::new);
    if (!o.getStatus().canMoveTo(Status.SHIPPED)) throw new Conflict("Order cannot be shipped");
    o.setStatus(Status.SHIPPED);
}
C#

ASP.NET Core. The rule lives in the domain class, so every caller goes through it.

With the weakness

[HttpPost("api/orders/{id}/status")]
public async Task<IActionResult> SetStatus(int id, StatusChange change)
{
    var order = await _db.Orders.FindAsync(id);
    order!.Status = change.Status;              // any status, any time
    await _db.SaveChangesAsync();
    return NoContent();
}

Fixed

public class Order
{
    static readonly Dictionary<Status, Status[]> Allowed = new()
    {
        [Status.Created] = new[] { Status.Paid, Status.Cancelled },
        [Status.Paid]    = new[] { Status.Shipped, Status.Cancelled },
        [Status.Shipped] = new[] { Status.Delivered },
    };
    public Status Status { get; private set; }

    public void MoveTo(Status next)
    {
        if (!Allowed.TryGetValue(Status, out var ok) || !ok.Contains(next))
            throw new InvalidOperationException($"Cannot move from {Status} to {next}");
        Status = next;
    }
}
Recommended practice
  • Write the allowed transitions down in one place, and test every transition that should be refused.
  • Check and update the state inside one database transaction, so two requests at once cannot both pass the check.
  • Record every state change in an audit log (Module 3), which also deals with repudiation.
